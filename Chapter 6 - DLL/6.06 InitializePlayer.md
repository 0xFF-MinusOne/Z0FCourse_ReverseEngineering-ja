# 6.06 Initialize Player

通常、DLL には一般的な目的があります。連結リストの設定、情報のログ記録、グラフィックスなどに使われる DLL かもしれません。いまリバースしている DLL は、1つの一般的な作業にとどまらないことをします。これは、簡単な例を使って DLL のリバースを紹介したかったからです。`InitializePlayer`、`PrintPlayerStats`、`MysteryFunc` の各関数はすべて互いに関連している、とお伝えしておきます。繰り返しますが、この DLL は学習用の道具です。もっと良い例は後ほど取り上げます。

それでは始めましょう。

`Player` に関連する関数が2つあるようです。`Player` はおそらく構造体(struct)です。それを確かめるには、`Player` 構造体を使う関数をリバースして、何で構成されているかを調べる必要があります。`InitializePlayer` から始めましょう。おそらくいちばん多くの情報が得られるからです。また、`Player` 構造体に最低限何が必要なのかも分かるはずです。

> 構造体とクラスは同じものです。違いは、デフォルトで一方が private、もう一方が public であることだけです。それ以外は、どちらもまったく同じように動作します。C++ の話をするときは、class と struct を区別せずに使って構いません。C にはクラスがないので、C の話をするときは class の代わりに struct を使ってください。

## Reversing(リバース)

### Function Signature(関数シグネチャ)

x64dbg の解析のおかげで、関数の宣言を確認できます。

* `void __cdecl InitializePlayer(class Player * __ptr64)`

つまり、この関数は void を返し、`Player` クラスへのポインタを取ります。まだ知らなければお伝えしますが、クラス/構造体の最初の要素を参照するには、クラスのベースを使います。次のように考えるとよいでしょう。

* `Player` = 最初の要素。
* `Player` + X = オフセット X にある要素。たとえば、最初の要素が32ビットの値なら、2番目の要素は `Player` + 0x4(32ビット)にあります。

### Disassembly(逆アセンブル)

アセンブリコードを見て、何が起きているのか考えましょう。

これが逆アセンブルした InitializePlayer 関数です。

```asm
00007FF930D01F2 MOV DWORD PTR DS:[RCX], 0x20
00007FF930D01F2 LEA RDX, QWORD PTR DS:[0x7FF930D39718]
00007FF930D01F2 MOV DWORD PTR DS:[RCX+0x4], 0x42C80000
00007FF930D01F3 MOV R8D, 0xB
00007FF930D01F3 ADD RCX, 0x8
00007FF930D01F3 JMP <dll.sub_7FF930D033C0>
```

* `MOV DWORD PTR DS:[RCX], 0x20` - 0x20(10進数で32)を、新しい `Player` クラスの最初の要素に移します。このことから、`Player` の最初の要素はおそらく整数だと分かります。
* `LEA RDX, QWORD PTR DS:[0x7FF930D39718]` - 文字列「PLACEHOLDER」へのアドレスを RDX にロードします。
* `MOV DWORD PTR DS:[RCX + 0x4], 0x42C80000` - 0x42C80000 を `Player` オブジェクトの2番目の要素に移します。最初の要素が4バイトの整数だったことが分かっています。0x42C80000 は奇妙な値に見えます。この値を float として見ると、100 のようです。この関数は「Player」を初期化するので、ゲームに関係があるのかもしれません。100 は最大体力の値としてよく使われます。そこで今のところ、0x42C80000 は float だと仮定できます。確かめるには、この値が浮動小数点レジスタ(XMM#)で扱われることがあるかを調べるとよいでしょう。

次の部分は怪しいです。何らかの関数呼び出しのようですが、ジャンプを使っています。

* `MOV R8D, 0xB` - 0xB は10進数で11で、これは「PLACEHOLDER」という文字列の長さでもあります。
* `ADD RCX, 0x8` - RCX に 0x8 が加えられます。今のところあまり意味が分かりませんが、結局のところこれは、初期化済みの最初の2つの要素を越えた位置に RCX を設定するためのものだと分かります。

ジャンプを追って、何が起きるか見てみましょう。

## Code Jumped To(ジャンプ先のコード)

`InitializePlayer` からジャンプする先のコードを見てみましょう。

```asm
00007FF930D033C PUSH RBX
00007FF930D033C PUSH RSI
00007FF930D033C PUSH RDI
00007FF930D033C PUSH R14
00007FF930D033C PUSH R15
00007FF930D033C SUB RSP, 0x20
00007FF930D033C MOV R14, QWORD PTR DS:[RCX+0x18]
00007FF930D033D MOV RSI, R8
00007FF930D033D MOV R15, RDX
00007FF930D033D MOV RBX, RCX
00007FF930D033D CMP R8, R14
00007FF930D033D JA dll.7FF930D03409
00007FF930D033D MOV RDI, RCX
00007FF930D033E CMP R14, 0x10
00007FF930D033E JB dll.7FF930D033EA
00007FF930D033E MOV RDI, QWORD PTR DS:[RCX]
00007FF930D033E MOV QWORD PTR DS:[RCX+0x10], RSI
00007FF930D033E MOV RCX, RDI
00007FF930D033F CALL <dll.sub_7FF930D0A4A0>
00007FF930D033F MOV RAX, RBX
00007FF930D033F MOV BYTE PTR DS:[RSI+RDI], 0x0
00007FF930D033F ADD RSP, 0x20
00007FF930D0340 POP R15
00007FF930D0340 POP R14
00007FF930D0340 POP RDI
00007FF930D0340 POP RSI
00007FF930D0340 POP RBX
00007FF930D0340 RET
```

このジャンプは明らかに呼び出しのように動作しています。実は、前のセクションにはプロローグがありませんでしたが、こちらにはあります。少し奇妙ですが、コンパイラは奇妙なことをしがちです。

これをリバースし始める前に、何が起きているか予想してみてください。文字列が渡され、おそらく文字列の長さと思われるものも渡されています。関数名「InitializePlayer」から考えると、この関数は文字列「PLACEHOLDER」を新しい Player クラスにコピーするのだろうと思います。そのためには、ある場所から別のメモリ位置へ文字列をコピーする必要があります。メモリの確保も扱うかもしれません。

* プッシュ - レジスタを保存するために、いくつかプッシュが行われています。
* `MOV R14, QWORD PTR DS:[RCX + 0x18]` - `Player` オブジェクトのオフセット 0x18 にあるデータをコピーします。Player+0x18 が何なのかは今のところ分かりません。
* ほかにも移動がいくつか行われていますが、見れば分かる内容です。
* `CMP R8, R14` - R8(0xB)と R14(RCX + 0x18)を比較します。
  * `JA dll.7FF930D03409` - JA(Jump if Above)は JG(Jump if Greater)と同じですが、符号なしの場合に使われます。このジャンプは、0xB と RCX + 0x18 にあるものを比較しています。この DLL を使うプログラムをデバッグすれば RCX + 0x18 に何があるか分かりますが、今は分からないまま進めましょう。

このジャンプの行き先をちょっと覗いてみましょう。

```asm
00007FF93790340 MOV RDI, 0x7FFFFFFFFFFFFFFF
00007FF93790341 CMP RSI, RDI
00007FF93790341 JA dll.7FF930D03505
```

0x7FFFFFFFFFFFFFFF が RDI に移され、その後 RSI がそれと比較されます。RSI は、文字列の長さだと推測しているものです。RSI が RDI より大きければジャンプします。そのジャンプを追うと呼び出しにたどり着き、その呼び出しを追うと次のようになります。

```asm
00007FF93790592 SUB RSP, 0x28
00007FF93790592 LEA RCX, QWORD PTR DS:[0x7FF930D39790] ; "string too long"
00007FF93790592 CALL dll.7FF930D05EB8
```

これは分かりやすいです。このジャンプはエラー処理を扱っているのです。このことから、いま見ていたコードは、何らかのコピーか確保を行うものだとほぼ確実に言えます。また、RCX+0x18 は文字列の長さの最大サイズのようなものだろうとも分かります。

元の場所に戻りましょう。

* `CMP R14, 0x10` - R14(RCX + 0x18)と 0x10(16)を比較します。繰り返しますが、RCX + 0x18 に何があるのかは分かりません。前のジャンプ条件は失敗の条件だったので、R8 は R14 より小さい、つまり 0xB は RCX+0x18 より小さいと仮定できます。
  * `JB dll.7FF930D033EA` - RCX + 0x18 が 16 未満(より小さい)ならジャンプします。
* `CALL <dll.sub_7FF930D0A4A0>` - この呼び出しの前の命令は興味深いです。前のジャンプ(`JB dll.7FF930D033EA`)が実行*される*と、player クラスの最初の要素である 32 は RDI にコピー*されません*。これは、文字列に十分な空き容量があることを確認していると仮定できます。
* `MOV QWORD PTR DS:[RCX+0x10], RSI` - RSI(0xB)を RCX + 0x10 に入れます。
* `MOV RCX, RDI` - RDI(`InitializePlayer` の RCX、つまり `Player` 構造体)を RCX に移します。これは、最初のコード部分の `ADD RCX, 0x8` 命令による RCX + 8 ではなく、元の RCX に戻します。
* その後、別の関数が呼び出されます。

この関数の残りはあまり面白くなさそうなので、その呼び出しを追って、何をするのか見てみましょう。その関数は次のとおりです。

```asm
00007FF930D0A4A MOV R11, RCX
00007FF930D0A4A MOV R10, RDX
00007FF930D0A4A CMP R8, 0x10
00007FF930D0A4A JBE dll.7FF930D0A500
<snip>
```

この場合は必要ないので、関数の全体は示しません。

* RCX(`Player`)が R11 に移されます。
* RDX(「PLACEHOLDER」文字列)が R10 に移されます。
* `CMP R8, 0x10` - 0xB と 0x10 を比較します。
  * `JBE dll.7FF930D0A500` - R8 が 0x10 以下ならジャンプします。**R8 は 0xB で、0x10 より小さいと分かっています。そこで、ジャンプを追いましょう。**

ジャンプ先は次のとおりです。

```asm
00007FF930D0A50 MOV RAX, RCX
00007FF930D0A50 LEA R9, QWORD PTR DS:[0x7FF930D00000]
00007FF930D0A50 MOV ECX, DWORD PTR DS:[R9+R8*4+0x45000]
00007FF930D0A51 ADD RCX, R9
00007FF930D0A51 JMP RCX
```

* `MOV RAX, RCX` - `Player` を RAX に移します。
* `LEA R9, QWORD PTR DS:[0x7FF930D00000]` - ダンプで 0x7FF930D00000 を辿ると、これがバイナリの先頭だと分かります。先頭に「MZ」があることから分かります。
* `MOV ECX, DWORD PTR DS:[R9 + R8 * 4 + 0x45000]` - 経験があれば、何が起きているか分かるはずです。R9 はバイナリのベースです。R8 は文字列のサイズです。0x45000 は何らかのオフセットで、おそらくデータ格納領域へのオフセットです。実際、少し計算してメモリマップ/セクションの位置を見ると、確かに RDATA セクションへのオフセットだと分かります。
* `ADD RCX, R9` - バイナリのベースである R9 を、R9 + R8 * 4 + 0x45000 にあったものに加えます。
* `JMP RCX` - これで、前の数命令の意味が分かります。それらの命令は、呼び出す関数のオフセット/アドレスを取得していたに違いありません。

次に、呼び出しの行き先を見つける必要があります。計算してみましょう。

* R9 + R8*4 + 0x45000 = 0x7FF930D00000 + 0x2C + 0x45000 = 0x7FF930D4502C  
* [0x7FF930D4502C] + 0x7FF930D00000 = A550 + 0x7FF930D00000 = 0x7FF930D0A550

簡単な補足です。必要なのは 0x7FF930D4502C *にある*値です。x64dbg では、ダンプのウィンドウで右クリックし、「Go to」を選び、「Expression」を選べます。0x7FF930D4502C の値を見ると 0x50A5 になっています。しかし、お使いのアーキテクチャはおそらくリトルエンディアンなので、A550 に反転させる必要があります。そうして得られたアドレスが 0x7FF930D0A550 です。逆アセンブルのウィンドウで右クリックして「Go to」を選び、「Expression」を選ぶと、そこへ移動できます。

新たに見つけたコードの逆アセンブルは次のとおりです。

```asm
00007FF930D0A55 MOV R8, QWORD PTR DS:[RDX]
00007FF930D0A55 MOVZX ECX, WORD PTR DS:[RDX+0x8]
00007FF930D0A55 MOVZX R9D, BYTE PTR DS:[RDX+0xA]
00007FF930D0A55 MOV QWORD PTR DS:[RAX], R8
00007FF930D0A55 MOV WORD PTR DS:[RAX+0x8], CX
00007FF930D0A56 MOV BYTE PTR DS:[RAX+0xA], R9B
00007FF930D0A56 RET
```

これで、文字列がコピーされる箇所が分かりました。全体を詳しくは説明しません。一連のコピーにすぎないからです。

まだ終わりではありません! 一連のリターン(辿るととても気持ちがいい)を辿って、元のコードがジャンプした先のコードに戻りましょう。

```asm
00007FF930D033C PUSH RBX
00007FF930D033C PUSH RSI
00007FF930D033C PUSH RDI
00007FF930D033C PUSH R14
00007FF930D033C PUSH R15
00007FF930D033C SUB RSP, 0x20
00007FF930D033C MOV R14, QWORD PTR DS:[RCX+0x18]
00007FF930D033D MOV RSI, R8
00007FF930D033D MOV R15, RDX
00007FF930D033D MOV RBX, RCX
00007FF930D033D CMP R8, R14
00007FF930D033D JA dll.7FF930D03409
00007FF930D033D MOV RDI, RCX
00007FF930D033E CMP R14, 0x10
00007FF930D033E JB dll.7FF930D033EA
00007FF930D033E MOV RDI, QWORD PTR DS:[RCX]
00007FF930D033E MOV QWORD PTR DS:[RCX+0x10], RSI
00007FF930D033E MOV RCX, RDI
00007FF930D033F CALL <dll.sub_7FF930D0A4A0> ; 今ここから来た
00007FF930D033F MOV RAX, RBX                ; 今ここにいる
00007FF930D033F MOV BYTE PTR DS:[RSI+RDI], 0x0
00007FF930D033F ADD RSP, 0x20
00007FF930D0340 POP R15
00007FF930D0340 POP R14
00007FF930D0340 POP RDI
00007FF930D0340 POP RSI
00007FF930D0340 POP RBX
00007FF930D0340 RET
```

これで、ほぼ終わりです。最後に指摘しておきたいのは `MOV BYTE PTR DS:[RSI+RDI], 0x0` で、これは文字列の末尾にヌルバイトを追加します。ご存じない方のために言うと、これが文字列の終端の仕方です。

## Summary(まとめ)

* 最初のメンバーは 0x20(10進数で32)に初期化されます。
* 2番目のメンバーは float で、100 に初期化されます。
* 最後に、3番目のメンバーは文字列で、「PLACEHOLDER」に初期化されます。このメンバーを初期化するために、ある場所から別の場所へ文字列をコピーする大量のコードが実行されます。
関数はソースコードでは次のようなものだと仮定できます。

```c++
class Player{
public:
  int member1;
  float health;
  string str; //std::string か char* などの可能性があり、確実ではない。
};

void InitializePlayer(Player* player){
  player->member1 = 32;
  player->health = 100.0f;
  player->str = "PLACEHOLDER";
}
```

しかし、文字列の初期化コードはどうなのでしょうか。考えてみてください。開発者が自分で初期化コードを書くでしょうか。おそらく書きません。それより可能性が高いのは、文字列がそのプログラミング言語の特別なデータ型で、そのコードが事前に生成されていたことです。たとえば、C++ の `std::string` ならそうなります。

実際のソースコードは次のとおりです(繰り返しますが、私が書いたので持っています)。

```c++
class Player {
public:
 int score;
 float health;
 std::string name;
};

void InitializePlayer(Player* player) {
 player->score = 32;
 player->health = 100.0f;
 player->name = "PLACEHOLDER";
}
```

的中しました!

## Final Notes(最後に)

これは、これまでよりもずっと複雑な例でした。分からなくなったときは、自分でコードをステップ実行するのがいちばんです。そして、コメントを書き、メモを取ることを忘れずに! 正直なところ、少し分かりにくかったので、苦戦しても心配しないでください。いつものように、質問には答えます。
