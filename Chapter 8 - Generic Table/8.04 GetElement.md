# 8.04 Get Element

次は、テーブルからデータを検索することに関係する関数を見てみましょう。どの関数を先にリバースするかは重要ではないことを思い出してください。私は、進めるのに良い順序だと思うものに基づいて選んでいます。

テーブルから何かを取得しそうな関数は複数あります。`RtlEnumerateGenericTable`、`RtlGetElementGenericTable`、`RtlLookupElementGenericTable` などです。名前からは、`RtlGetElementGenericTable` か `RtlLookupElementGenericTable` がいちばん簡単だと思います。その2つのうち、`RtlGetElementGenericTable` が最も単純だろうと推測します。この関数が名前のとおりに動作するなら、おそらく2つのパラメータを取ります。Generic Table へのポインタと、検索するインデックスです。

`RtlGetElementGenericTable` の逆アセンブルは次のとおりです。

```asm

00007FFD3F0DC1B5 MOV R10D, DWORD PTR DS:[RCX+0x20]
00007FFD3F0DC1B9 LEA R11D, QWORD PTR DS:[RDX+0x1]
00007FFD3F0DC1BD MOV R8, QWORD PTR DS:[RCX+0x18]

00007FFD3F0DC1C4 MOV R9D, R11D
```

この関数に入る前にヒントを出します。そうしないと、とても混乱するかもしれません。ヒントが要らない場合は、先に進んでください。ヒントが欲しいか迷っている場合は、これはコンピュータサイエンスのトピックに関係している、とお伝えしておきます。もっと具体的には、データ構造です。それでは、ネタバレです。この関数はスプレー木(splay-tree)を扱います。ここでの目的では、連結リストとして見て構いません。リバースしても分かりますが、これらのトピックを知らないととても混乱します。必要なら、続ける前にこれらのトピックを学んできてください。

### General Overview(全体像)

関数がかなり複雑な場合、私はまず分かりやすい部分を見て、それから戻ってさらに詳しく分析するようにしています。そうすると、詳細に入る前に、何が起きているのか大まかに把握できます。最初にやるのは、関数のパラメータの確認です。

* RCX はデータ構造として使われている(`MOV EAX, DWORD PTR DS:[RCX+0x24]`)ので、いつものようにおそらくテーブルです。
* RDX も使われていますが、オフセット +0x1 が付いています(`LEA R11D, QWORD PTR DS:[RDX+0x1]`)。RDX はデータ構造かもしれませんが、この場合は RDX がインクリメントされているように見えます。
* R8 と R9 は上書きされているので、おそらくパラメータではありません。
この関数が取るパラメータは2つだけだと推測できます。1つ目はテーブル、2つ目は推測にすぎませんが、おそらく検索するインデックスです。

興味深いジャンプが2つあり、どちらも `ntdll.7FFD3F0DC21C` に向かいます。`ntdll.7FFD3F0DC21C` は戻り値をゼロにして、RBX が復元される `ntdll.7FFD3F0DC204` にジャンプします。最後に、関数がリターンします。これはおそらく失敗の条件です。

>まだやっていなければ、リバースエンジニアリングをしながらメモや疑似コードを書くことを強くお勧めします。

# Part 1

次のコードの部分に注目しましょう。

```asm
00007FFD3F0DC1B0 MOV QWORD PTR SS:[RSP+0x8], RBX
00007FFD3F0DC1B5 MOV R10D, DWORD PTR DS:[RCX+0x20]
00007FFD3F0DC1B9 LEA R11D, QWORD PTR DS:[RDX+0x1]
00007FFD3F0DC1BD MOV R8, QWORD PTR DS:[RCX+0x18]
00007FFD3F0DC1C1 OR EBX, 0xFFFFFFFF
00007FFD3F0DC1C4 MOV R9D, R11D
00007FFD3F0DC1C7 CMP EDX, EBX
00007FFD3F0DC1C9 JE ntdll.7FFD3F0DC21C
00007FFD3F0DC1CB MOV EAX, DWORD PTR DS:[RCX+0x24]
00007FFD3F0DC1CE CMP R11D, EAX
00007FFD3F0DC1D1 JA ntdll.7FFD3F0DC21C
```

* `MOV QWORD PTR SS:[RSP+0x8], RBX` は、RBX をスタックに保存/退避します。
* `MOV R10D, DWORD PTR DS:[RCX+0x20]` は、Table->Member5 を R10D に移します。
* `LEA R11D, QWORD PTR DS:[RDX+0x1]` は興味深い命令です。基本的に `R11D = RDX + 1` です。これは、RDX の値を保持するために、`INC` の代わりに使っているのかもしれません。**R11D を AdjustedIndex と呼びましょう**。また、これは有用な情報をもう1つ教えてくれます。インデックスはゼロ始まりだということです。つまり、一般的な配列と同様に、1ではなくインデックス0から始まります。インデックスと違って、要素数はゼロ始まりでは*ありません*(要素が0個なら空です)。配列には3つの要素があっても、array[0]、array[1]、array[2] でアクセスします。
* `MOV R8, QWORD PTR DS:[RCX+0x18]` は、Table->Member4 を R8 に移します。
* `OR EBX, 0xFFFFFFFF` は、EBX を -1 に設定します。
* `MOV R9D, R11D` - R11D(AdjustedIndex)を R9D に移します。これも最初は少し奇妙です。なぜ R11D をそのまま使わないのでしょうか。おそらく R11D を保持するためです。言い換えると、変更されないものと、変更されるものを1つずつ持っておくためです。
* `CMP EDX, EBX` は、EDX(検索するインデックス)と EBX(-1)を比較します。
  * インデックスが -1 なら、失敗の条件である `ntdll.7FFD3F0DC21C` にジャンプします。
* `MOV EAX, DWORD PTR DS:[RCX+0x24]` は、Table->NumberOfElements を EAX に移します。これは、Table->NumberOfElements が4バイトだという考えを裏付けます。ここでも +0x24 のオフセットで参照されており、4バイトのレジスタに移されているからです。
* `CMP R11D, EAX` - 次に、R11D(AdjustedIndex)が EAX(NumberOfElements)より大きいかどうかを確認します。これもインデックスの検証です。
  * R11D が EAX より大きければ、失敗の条件にジャンプします。`JG` *ではなく* `JA` が使われているので、符号なしだと分かります。

今見たものの疑似コードは次のとおりです。

```c
ULONG adjustedIndex = index + 1;
if(index == -1 || adjustedIndex > Table->NumberOfElements){
    return 0;
}
```

# Part 2

先ほどの続きです。

```asm
7FF8BBD1C1D3 CMP R11D, R10D   ; CMP AdjustedIndex, Table->Member5
7FF8BBD1C1D6 JE ntdll.7FFD3F0DC200
7FF8BBD1C1D8 JB ntdll.7FFD3F126C7A
7FF8BBD1C1DE SUB EAX, R11D    ; EAX = Table->NumberOfElements - AdjustedIndex
7FF8BBD1C1E1 MOV EDX, R11D
7FF8BBD1C1E4 SUB EDX, R10D
7FF8BBD1C1E7 INC EAX
7FF8BBD1C1E9 CMP EDX, EAX
```

ここから面白くなってきます。

* `CMP R11D, R10D` は、AdjustedIndex をテーブルの5番目のメンバーと比較します。このことから、テーブルの5番目のメンバーは何らかのインデックスだと考えられます。最後のインデックス、最初のインデックス、以前に見つかったインデックス、あるいは特別なインデックスを保持しているのかもしれません。何であれ、いずれ分かります。
  * 等しければ、`ntdll.7FFD3F0DC200` にジャンプします。
  * AdjustedIndex が5番目のメンバーより小さければ(JB は Jump if Below)、`ntdll.7FFD3F126C7A` にジャンプします。
    * これらのジャンプ先は後で考えます。これらのジャンプが行われなかったものとして進めます。つまり、Index+1 は Table->Member5 より大きいということです。
* `SUB EAX, R11D` - EAX には Table->NumberOfElements が入っています。この命令は実質的に `EAX = Table->NumberOfElements - AdjustedIndex` です。
* `MOV EDX, R11D` は、R11D(AdjustedIndex)を EDX にコピーします。これも保持の例です。
* `SUB EDX, R10D` は `EDX = AdjustedIndex - Table->Member5` と同じです。
* `INC EAX` は `EAX = (Table->NumberOfElements - AdjustedIndex) + 1` と同じです。
* `CMP EDX, EAX` は、EDX(AdjustedIndex - Table->Member5)と EAX(Table->NumberOfElements - AdjustedIndex)を比較します。Table->NumberOfElements - AdjustedIndex は、最大/最後のインデックスと要求されたインデックスとの差であることに注意してください。
* その後、一連の条件ジャンプがあります。先に進む前に、今起きたことをもう少し理解しておきましょう。

何が起きているかを理解しやすくするために、テスト値を使って見てみましょう。Table->NumberOfElements が10、インデックスが2だとします。Table->Member5 が何かはまだ分かりませんが、よい推測を立て始められます。

```asm
7FF8BBD1C1D3 CMP 3, Table->Member5
7FF8BBD1C1D6 JE ntdll.7FFD3F0DC200
7FF8BBD1C1D8 JB ntdll.7FFD3F126C7A
7FF8BBD1C1DE EAX = Table->NumberOfElements - 3
7FF8BBD1C1E4 EDX = 3 - Table->Member5
7FF8BBD1C1E7 EAX++
7FF8BBD1C1E9 CMP EDX, EAX    ; CMP (3 - Table->Member5) to (Table->NumberOfElements - 3).
```

さて、ここから Member5 が何なのか予測できます。何らかのインデックスです。考えられるシナリオをいくつか見てみましょう。

Member5 が最大のインデックスの場合:

```asm
CMP (3 - 10) to (10 - 3)
```

Member5 が最小のインデックスの場合:

```asm
CMP (3 - 1) to (1 - 3)
```

Member5 が最後に見つかったインデックス(たとえば 7)の場合:

```asm
CMP (3 - 7) to (7 - 3)
```

Member5 が最小のインデックスだとしても、役に立つ目的はありません。最大のインデックスでも、あまり役に立たないでしょう。しかし、最後に見つかったインデックスなら、かなり役に立つ可能性があります。たとえば、インデックスと最後に見つかったインデックスが同じなら、最後に見つかったインデックスをそのまま返せます。インデックスが最後に見つかったインデックスより大きければ、最後に見つかったインデックスより上を探せばよいと分かります。インデックスが最後に見つかったインデックスより小さければ、その下を探します。これでパフォーマンスが向上します。まだ確信は持てませんが、Member5 は最後に見つかったインデックスだという仮定で続けましょう。

続くジャンプを見ると、このシナリオはさらに可能性が高く思えます。

# Part 3

```asm
7FF8BBD1C1E9 CMP EDX, EAX   ; CMP (AdjustedIndex - Table->Member5) to (Table->NumberOfElements - AdjustedIndex).
7FF8BBD1C1EB JA ntdll.7FFD3F0DC20A
7FF8BBD1C1ED TEST EDX, EDX
7FF8BBD1C1EF JE ntdll.7FFD3F0DC1F8
7FFD3F0DC1F1 MOV R8, QWORD PTR DS:[R8]
7FF8BBD1C1F4 ADD EDX, EBX
7FF8BBD1C1F6 JNE ntdll.7FFD3F0DC1F1
7FF8BBD1C1F8 MOV QWORD PTR DS:[RCX+0x18], R8
7FF8BBD1C1FC MOV DWORD PTR DS:[RCX+0x20], R11D
7FF8BBD1C200 LEA RAX, QWORD PTR DS:[R8+0x10]
7FFD3F0DC204 MOV RBX, QWORD PTR SS:[RSP+0x8]
7FF8BBD1C209 RET
7FF8BBD1C20A LEA R8, QWORD PTR DS:[RCX+0x8]
7FF8BBD1C20E TEST EAX, EAX
7FF8BBD1C210 JE ntdll.7FFD3F0DC1F8
7FFD3F0DC212 MOV R8, QWORD PTR DS:[R8+0x8]
7FF8BBD1C216 ADD EAX, EBX
7FF8BBD1C218 JE ntdll.7FFD3F0DC1F8
7FF8BBD1C21A JMP ntdll.7FFD3F0DC212
7FF8BBD1C21C XOR EAX, EAX
7FF8BBD1C21E JMP ntdll.7FFD3F0DC204
```

* `JA ntdll.7FFD3F0DC20A` - 比較の結果、EDX が EAX より大きければ、`ntdll.7FFD3F0DC20A` にジャンプします。
  * そのジャンプを追ってみましょう。
    * `LEA R8, QWORD PTR DS:[RCX+0x8]` は、R8 を Table->Member2 のアドレスに設定します。
    * `TEST EAX, EAX` は、EAX がゼロかどうかをテストします。EAX は Table->NumberOfElements - AdjustedIndex です。これも、最後のインデックスと現在要求されているインデックスとの差です。
    * EAX がゼロ*なら*、`ntdll.7FFD3F0DC1F8` にジャンプします。EAX がゼロということは、Table->NumberOfElements - AdjustedIndex = 0 ということです。これは、要求された要素が最初の要素だったことを意味します。
      * `MOV QWORD PTR DS:[RCX+0x18], R8` は、R8(Table->Member2 のアドレス)を Table->Member4 に移します。
      * `MOV DWORD PTR DS:[RCX+0x20], R11D` は、AdjustedIndex を Table->Member5 に移します。これは Member5 を AdjustedIndex、つまりたった今見つけたインデックスに設定しています。このことから、Member5 はほぼ間違いなく、最後に見つかった要素/インデックスです。**間違いだと証明されるまで、Table->Member5 を Table->LastIndexFound と宣言しましょう。**
      * `LEA RAX, QWORD PTR DS:[R8+0x10]` は、RAX に R8+0x10 のアドレスをロードします。R8 は Table->Member2 のアドレスだったことを思い出してください。先に進む前に、少し考えてみましょう。3つのポインタ、Table->Member2、Table->Member3、Table->Member4 は、すべて何らかの形で関連していると、かなり確信できます。Table->Member3 が使われるのはまだ見ていませんが、Member2 と 4 が関連しているなら、おそらく Member3 もそうでしょう。そのうえで、+0x10 というオフセットに注目してください。R8 はすでに Table->Member2 なので、+0x10 のオフセットは興味深いものです。これらのポインタが、同じように関連した3つのポインタを持つ別のデータ構造を指しているなら、このオフセットは、それらをうまく飛び越えます。ヘッダを持つデータ構造はよくあり、そのヘッダはプログラマーから隠されたり除外されたりすることがよくあります。繰り返しますが、確信は持てませんが、覚えておくべきことです。
      * `MOV RBX, QWORD PTR SS:[RSP+0x8]` は RBX を復元します。
      * `RET`
      * 私たちが扱っているのは、リストや何らかの木のような、一連のポインタのようです。この関数は、同じような3つのポインタの組を持つ別のデータ構造へのポインタと思われるものを返します。この関数の目的は、インデックスを取得することだと思い出してください。このテーブルは、何らかの連結リストの一部か、内部に連結リストを持っているのかもしれません。関数をそう見ると、そうなっているように思えます。そこで、今のところそう考えて進めます。また、Member4 とその使われ方を見てみましょう。これは、最後に見つかった要素のようです。このコードの部分では、リターンする前にそれが設定されているからです。**Table->Member4 を Table->LastElementFound と宣言しましょう。** はっきりさせておくと、Table->LastElementFound は最後に見つかった要素へのポインタで、Table->LastIndexFound は最後に見つかったインデックスの番号です。
    * EAX がゼロ*でなければ*、続行します。
      * `MOV R8, QWORD PTR DS:[R8+0x8]` は、R8+0x8 が指すものを R8 に移します。これはとても興味深いです。
      * `ADD EAX, EBX` は、EAX(Table->NumberOfElements - AdjustedIndex)と EBX(-1)を足します。これは1を引くのと同じです。ご存じなければお伝えすると、ADD 命令はさまざまなフラグをセットし、それらは比較命令で使えます。
      * `JE ntdll.7FFD3F0DC1F8`。`TEST EAX, EAX` の後の `JE` を追ったときに、`ntdll.7FFD3F0DC1F8` のコードはすでにリバースしました。`ntdll.7FFD3F0DC1F8` は、成功してリターンする処理のようです。
      * `JMP ntdll.7FFD3F0DC212` 前のジャンプが行われなければ、`ntdll.7FFD3F0DC212` への無条件ジャンプがあります。そこは、いまリバースしている小さなセクションの先頭です。つまり、これはループです。最後の要素と要求されたインデックスとの差からカウントダウンしています。これは、何らかの連結リストを扱っていることも裏付けます。`MOV R8, QWORD PTR DS:[R8+0x8]` という命令は、R8+0x8 が指すものを R8 に移すものだったことを思い出してください。この無条件ジャンプが行われると、その命令が再び実行されます。要求されたインデックスに到達するのに必要な回数だけ、ポインタの連鎖を辿っているのです。

このコードのかたまりの先頭、`CMP EDX, EAX` に戻りましょう。AdjustedIndex - Table->LastIndexFound が Table->NumberOfElements - AdjustedIndex より大きい場合に何が起きるかが分かりました。言い換えると、要求されたインデックスが、最後に見つかったインデックスよりリストの末尾に近い場合に起きることです。次は、要求されたインデックスが最後に見つかったインデックスに近い場合に何が起きるかを見てみましょう。

* `TEST EDX, EDX` は、EDX(AdjustedIndex - Table->LastIndexFound)がゼロかどうかをテストします。ゼロなら、`ntdll.7FFD3F0DC1F8` にジャンプします。
* `JE ntdll.7FFD3F0DC1F8` - 等しければ、最後に見つかったインデックスをそのまま返します。このコードはすでにリバースしたので、先に進みます。
* `MOV R8, QWORD PTR DS:[R8]` 先ほどと似た状況です! R8 が指すものを R8 に移しています。これはポインタの連鎖を下っていきます。これは、先ほど見つけた R8+0x8 とは別のポインタの連鎖であることに注意してください。これは連結リストの Flink と Blink を示しています。
* `ADD EDX, EBX` は、AdjustedIndex - Table->LastIndexFound と -1 を足します。これは値をデクリメントします。
* `JNE ntdll.7FFD3F0DC1F1` 等しくなければ、続行します!

では、Flink と Blink が使われているとして、この場合はどちらが使われているでしょうか。そのコードが実行されるなら、AdjustedIndex - LastFoundIndex < NumberOfElements - AdjustedIndex です。言い換えると、要求されたインデックスは、最後のインデックスより LastFoundIndex に近いということです。論理で考えるか、数値を式に当てはめてみれば、これは Flink に違いないと分かります。

AdjustedIndex(5) - LastFoundIndex(3) < NumberOfElements(10) - AdjustedIndex(5)
5 - 3 < 10 - 5
2 < 5

5に到達するには、Flink を辿る必要があります。

これで、何が起きているのか分かりました。ポインタは連結リストの一部です。関数のこの部分は、インデックスを取得する最も効率的な方法を決める多くの条件の1つにすぎません。

# Part 4

さて、ずっと前に戻る時間です。先ほどは2つのジャンプを飛ばしたので、見直しましょう。

```asm
7FF8BBD1C1D3 CMP R11D, R10D           ; R11D = AdjustedIndex, R10D = Table->LastIndexFound
7FF8BBD1C1D6 JE ntdll.7FFD3F0DC200    ; THESE JUMPS
7FF8BBD1C1D8 JB ntdll.7FFD3F126C7A    ; THESE JUMPS
7FF8BBD1C1DE SUB EAX, R11D            ; EAX = Table->NumberOfElements

7FF8BBD1C1E4 SUB EDX, R10D
7FF8BBD1C1E7 INC EAX
7FF8BBD1C1E9 CMP EDX, EAX
```

`JE ntdll.7FFD3F0DC200` を追ってみましょう。

```asm
7FF8BBD1C200 LEA RAX, QWORD PTR DS:[R8+0x10]
7FFD3F0DC204 MOV RBX, QWORD PTR SS:[RSP+0x8]
7FF8BBD1C209 RET
```

このコードはすでにリバースしました。R8+0x10(R8 は Table->Member2)は、おそらく何らかのヘッダを飛ばしています。ヘッダを飛ばした後は、それが何のデータ構造であれ、そこへのポインタを返せます。その後、RBX を復元してリターンします。

Table->Member2 はおそらく連結リストの先頭へのポインタなので、そう呼ぶことにしましょう。Table->Member2 は、これから Table->LLHead です。

次に `JB ntdll.7FFD3F126C7A` を追います。

```asm
00007FFD3F126C7A MOV EAX, R10D
00007FFD3F126C7D SHR EAX, 0x1
00007FFD3F126C7F CMP R11D, EAX
00007FFD3F126C82 JBE ntdll.7FFD3F126C9B
00007FFD3F126C84 SUB R10D, R11D
00007FFD3F126C87 JE ntdll.7FFD3F0DC1F8
00007FFD3F126C8D MOV R8, QWORD PTR DS:[R8+0x8]
00007FFD3F126C91 ADD R10D, EBX
00007FFD3F126C94 JNE ntdll.7FFD3F126C8D
00007FFD3F126C96 JMP ntdll.7FFD3F0DC1F8
00007FFD3F126C9B LEA R8, QWORD PTR DS:[RCX+0x8]
00007FFD3F126C9F TEST R11D, R11D
00007FFD3F126CA2 JE ntdll.7FFD3F0DC1F8
00007FFD3F126CA8 MOV R8, QWORD PTR DS:[R8]
00007FFD3F126CAB ADD R9D, EBX
00007FFD3F126CAE JNE ntdll.7FFD3F126CA8
00007FFD3F126CB0 JMP ntdll.7FFD3F0DC1F8
```

* `MOV EAX, R10D` は、Table->LastIndexFound を EAX に移します。
* `SHR EAX, 0x1` は、EAX を1ビット右にシフトします。これは2で割るのと同じです。00110010 は 00011001 になります。
* `CMP R11D, EAX` は、AdjustedIndex を Table->LastIndexFound/2 と比較します。
  * AdjustedIndex <= Table->LastIndexFound/2 なら、`ntdll.7FFD3F126C9B` にジャンプします。これも、インデックスを取得する最も効率的な方法を探しています。範囲の前半にあるか後半にあるかを確認しているのです。**そのジャンプを追いましょう。**
    * `LEA R8, QWORD PTR DS:[RCX+0x8]`。Table->LLHead のアドレスを R8 にロードします。
    * `TEST R11D, R11D` は、R11D(AdjustedIndex)がゼロかどうかを確認します。
      * `JE ntdll.7FFD3F0DC1F8` - R11D がゼロなら、`ntdll.7FFD3F0DC1F8` にジャンプします。これは、成功してリターンするコードの部分です。Table->LastElementFound に見つかった要素を、Table->LastIndexFound に今検索したインデックスの番号を設定します。
    * 等しくなければ、先ほどと同じ状況になります。目的のインデックスに着くまでポインタの連鎖を辿るループになり、その後でその結果を返します。

  * AdjustedIndex > Table->LastIndexFound/2 なら:
    * `SUB R10D, R11D` は、Table->LastIndexFound から AdjustedIndex を引きます。
    * `JE ntdll.7FFD3F0DC1F8` - 等しければ、成功してリターンするコードの部分にジャンプします。
    * `MOV R8, QWORD PTR DS:[R8+0x8]` - 等しくなければ、ループして要素を取得します。

これで、何が起きているのか分かりました。与えられたインデックスの要素を取得する一連のループがあります。どのループが実行されるかは、最も効率的な方法がどれかで決まります。関数は Table->LastIndexFound と Table->LastElementFound の両方を設定します。そして、見つかった要素へのポインタを返します。

```c++
struct Table{
    QWORD Member1;  //テーブルに要素があるときはゼロ以外。
    LIST_ENTRY* LLHead;
    LIST_ENTRY* UnknownEntry;
    LIST_ENTRY* LastElementFound;
    ULONG LastIndexFound;
    ULONG NumberOfElements;
    QWORD Member7;
    QWORD Member8;
    QWORD Member9;    
};

void* MyRtlGetElementGenericTable(Table* table, ULONG index)
{
    // 変数の初期化:
    ULONG numberOfElements = table->NumberOfElements;
    LIST_ENTRY *elementFound = table->LastElementFound;
    ULONG lastIndexFound = table->LastIndexFound;
    ULONG adjustedIndex = index + 1;

    // インデックスの検証:
    if (index == -1 || adjustedIndex > numberOfElements){
        return 0;
    }

    // 最後に見つかった要素なら、要素を探さない。
    if (adjustedIndex != lastIndexFound)
    {
        // 目的の要素が lastElementFound でなければ、探す:
        if (lastIndexFound > adjustedIndex)
        {
            // どちらの方向に探すか決める:
            ULONG halfWay = lastIndexFound / 2;
            if (adjustedIndex > halfWay)
            {
                // lastElementFound から始めて、先頭に向かって後ろへ進む:
                ULONG elementsToGo = lastIndexFound - adjustedIndex;
                while(elementsToGo--){
                    elementFound = elementFound->Blink;
                }
            }
            else
            {
                // 先頭から始めて、前へ進む:
                ULONG elementsToGo = adjustedIndex;
                elementFound = (LIST_ENTRY *) &table->LLHead;
                
                while(elementsToGo--){
                    elementFound = elementFound->Flink;
                }
            }
        }
        // インデックスが lastIndexFound より大きい場合:
        else
        {            
            ULONG elementsToLastFound = adjustedIndex - lastIndexFound;
            ULONG elementsToEnd = numberOfElements - adjustedIndex + 1;

            // インデックスが lastIndexFound とリストの末尾のどちらに近いかを調べる:
            if (elementsToLastFound <= elementsToEnd)
            {
                // 要求されたインデックスは、最後に見つかった要素に近い。
                // lastElementFound から始めて、リストを前方へ探索する:
                while (elementsToLastFound--){
                    elementFound = elementFound->Flink;
                }
            }
            // 要素は、最後に見つかった要素よりリストの末尾に近い:
            else
            {
                // リストの先頭から始めて、後方へ探索する:
                elementFound = (LIST_ENTRY *) &table->LLHead;
                while (elementsToEnd--){
                    elementFound = elementFound->Blink;
                }
            }
        }
        // 見つかった要素とインデックスをテーブルに保存する:
        table->LastElementFound = elementFound;
        table->LastElementIndex = adjustedIndex;
    }

    // ヘッダを飛ばして、見つかった要素を返す:
    return elementFound + 0x10;
}
```
